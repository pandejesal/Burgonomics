## Symptom 1 — "Back on Stores closes the app" (in-app + Android hardware/gesture)

### 1a. Root cause — Android `backButton` treated `/stores` as an entry screen

`src/shared/platform/mobileBootstrap.ts` (pre-fix): the `isRoot` set used by the
`App.addListener("backButton", …)` handler was
`["/", "/splash", "/home", "/stores"]`, so **hardware/gesture back on Store
Selection called `App.minimizeApp()`** — the app visibly closed even though the
WebView still had history to pop. Rule violated: *back may only minimize from a
true entry screen, and only when there is nothing left to pop.*

**Fix** — `mobileBootstrap.ts:113-142`:

| Line | Change |
| --- | --- |
| 121–124 | derive the path from `window.location.hash` (hash history is active on native — `src/router.tsx` `shouldUseHashHistory`), then `pathOnly = path.split(/[?#]/)[0]` so `/home?from=x` still counts as Home |
| 125 | `isEntry = !pathOnly \|\| "/" \|\| "/splash" \|\| "/home"` — **`/stores` removed** |
| 127–131 | entry screen → `App.minimizeApp()` (unchanged behaviour for launch/splash/home) |
| 133–136 | any other path with history → `window.history.back()` |
| 138–141 | sub-route with nothing to pop (deep link / cold start) → `pushState({}, "", "#/home")` + `dispatchEvent(new PopStateEvent("popstate"))`, the same contract already used by the deep-link handler at `mobileBootstrap.ts:73` — the app stays alive on Home instead of terminating |

Ordering is unchanged: modal/sheet dismissal still wins first (`:87-111`).

### 1b. Root cause — no in-app back control on Store Selection

`src/routes/stores.tsx` (pre-fix) rendered `<AppShell … showTopBar={true}>`
without `backTo`. `TopBar` only draws the back `Link` when `backTo || onBack`
(`src/shared/navigation/TopBar.tsx:33-45`), so the header showed an **empty
placeholder** and the only way out was the OS back gesture — which, per 1a,
minimized the app.

**Fix** — `stores.tsx:309-316`:

```tsx
// In-app back: Store Selection sits behind Home in the stack, so the
// TopBar must render a real back control. Without `backTo` the header
// rendered an empty placeholder and the only way out was the OS back
// gesture. Gated on an existing selection so a cold launch (no store
// yet) can't bounce back to Home's `replace`-to-/stores redirect loop.
backTo={activeStore ? "/home" : undefined}
```

Gating rationale: `home.tsx` does `if (!store) → replace /stores`; if back were
unconditional on a cold launch with no selection it would ping-pong. With
`activeStore` set, back → `/home` → home renders normally.

**Acceptance mapping (symptom 1):** in-app back ✔ (`TopBar` Link), hardware/gesture
back ✔ (`history.back()`), never minimize from a sub-route ✔ (`isEntry` no longer
contains `/stores`), cold-start sub-route stays alive on Home ✔.

## Symptom 2 — "Product tap shows the wrong product / app frozen between UFO Burger, Sides, Cold Coffee"

Five independent defects, all in declared files:

### 2a. Stale product detail state (wrong product painted, stuck skeleton)

`src/routes/menu.product.$productId.tsx`: `state` was only mutated inside
`load()`, which runs in an effect keyed on `productId` — so for one commit after
navigation the **previous product's object** (qty, image, selections, price)
remained on screen. Worse, two in-flight loads had no ordering guard: a slow
older response could resolve last and overwrite a newer one, leaving the route
on a skeleton or another product's data indefinitely.

**Fix** (file lines below):

| Line | Change |
| --- | --- |
| 37 | `loadedFor?: string` added to `State` — records which `productId` the state belongs to |
| 63, 66, 72 | `loadSeq = useRef(0)`; `const seq = ++loadSeq.current` at call start and `if (seq !== loadSeq.current) return;` after `Promise.all` ⇒ a superseded response is dropped |
| 74, 78, 84 | every terminal branch stamps `loadedFor: productId` |
| 105–111 | effect resets `setQty(1)`, `setActiveImage(0)`, `setSelectedComboId(null)`, `setSelections({})` **before** `void load()` so nothing leaks between products |
| 117 | `const status = state.loadedFor === productId ? state.status : "loading"` |
| 180, 193, 201 | the three early-return branches gate on `status` (not raw `state.status`), so a different product's `ready` state can never satisfy the detail render |

Result: the route renders its own skeleton until *its own* data lands, and a
late stale response can never overwrite it.

### 2b. Transition class applied one frame late (`ConsumerRouteTransition`)

Pre-fix the direction was computed in a `useEffect`. Effects run *after* the
first paint of the freshly keyed screen (`key={pathname}`), so a pushed screen
first painted with the **previous** navigation's `route-transition-pop` class and
was swapped to `push` on the next frame — the animation restarted mid-flight and
screens looked frozen between routes.

**Fix** — `ConsumerRouteTransition.tsx`:

- `:39` `stateRef` keyed by pathname, `:50-62` direction computed **during
  render** into `stateRef` in the same pass that advances `isFirstLoad` /
  `isPopNavigation` / `lastPathname` (each consumed exactly once per change).
- `:45-48` mount-time effect (`[pathname]`) clears `isFirstLoad` and syncs
  `lastPathname`, so the first *navigation* still animates while first paint does not.
- `:66-67` class is read from `stateRef.current.transitionClass` during render —
  never from post-commit state.

### 2c. Pager race — the actual "frozen between A/B/C"

`src/routes/menu.index.tsx`: two effects fought over `scrollLeft`.

1. the scroll listener set `activeCategoryId` (rAF-debounced) as the user's
   momentum + `snap-mandatory` settling progressed;
2. a second effect then scrolled the windowed pager to `activeCategoryId`.

Pre-fix that second effect ran on **every** `activeCategoryId` change — including
the ones produced by (1) — and released `isProgrammaticScroll` on a blind
`550ms` timer. Mid-swipe the re-scroll cancelled momentum and retargeted the
windowed pager at an **intermediate (off-window, therefore blank) panel**; the
listener then re-anchored to that intermediate index. Net effect: view parked
between two categories showing blank panels, rail showing a different category
than the URL — the exact "frozen between UFO Burger / Sides / Cold Coffee" report.

**Fix** (`menu.index.tsx:181-271`):

| Line | Change |
| --- | --- |
| 191, 206, 227-232 | `scrollDrivenFor` ref: the scroll listener marks its own `setActiveCategory` call; the programmatic-scroll effect consumes that marker and returns without scrolling (also drops stale markers so they can't block a later intentional scroll) |
| 241-249 | computes `currentIndex`; uses `behavior: "auto"` when jumping **more than one panel** (off-window panels are unmounted — a long smooth scroll flies through blank space) and `"smooth"` for a single step |
| 251-270 | guard released on `scrollend` (with a 550ms `setTimeout` fallback for engines without it) instead of a blind timer; the timer/`scrollend` listener are always removed, and the cleanup **also clears the guard** so a stale `true` can never leave the pager ignoring user scrolls |
| 239 | early return when already within 4px — no-op re-renders don't restart animations |

### 2d. Blank panel when the active category has no bucket

`menu.index.tsx:273-280` (new effect): `buckets[activeCategoryId]` could be
missing (deep link, live category subscription, store switch), and the list's
loading sentinel only renders once the bucket exists → panel stayed blank forever
and the tap looked dead. The effect now primes it:
`if (!buckets[activeCategoryId]) void loadMore(activeCategoryId);`

Safe against loops: `menuStore.loadMore` sets `loading` synchronously and
creates the bucket entry before awaiting, so a concurrent call for the same id
returns immediately, and the effect re-run sees the bucket present.

### 2e. URL `?category=` was silently dropped (id-space mismatch)

Home's category pills ship **hard-coded ids** from
`CategoryPills.DEFAULT_CATEGORIES` (`all/burgers/wraps/combos/sides/beverages`),
while the menu's `?category=` was matched with strict equality against real
Petpooja/Firestore ids. `beverages` and `sides` (the tester's "Shakes", "Sides")
never matched → the URL category was discarded and the route fell back to
`categories[0]`.

**Fix** — `menu.index.tsx:32-70` `slugify()` + `resolveCategoryId(param,
categories)`: exact id → exact slug-of-name (`sides` → "Fries & Sides",
`beverages` → "Beverages & Shakes") → slug-token overlap, and it is now what the
URL-sync effect calls (`:137-145`). Unresolvable values fall back to the first
real category instead of silently no-opping.

**Acceptance mapping (symptom 2):** that product's detail ✔ (2a), no wrong
product ✔ (2a), no stuck half-transition ✔ (2b + 2c), visible failure instead of
a dead panel ✔ (2d).

## Symptom 3 — "Category shortcuts land on the wrong category"

Root cause = 2e above (fake pill ids vs. real id space). Fixed inside
`menu.index.tsx` with `resolveCategoryId`; no change was needed in
`CategoryPills.tsx` / `home.tsx` / `CategoryGrid.tsx` — those files are outside
the declared `files_touched` and the resolver on the consuming side covers every
caller.

Related, **deliberately not changed** (documented, not fixed): the home
`CategoryGrid` tiles call `setActiveCategory` + `navigate("/menu")` **without**
`?category=`. Because `menuStore.load()` preserves an `activeCategoryId` that is
a valid id, this works today; it would only mis-resolve if the grid's id space
differed. The grid reads `firestoreService.getCategories()` (Firestore
`categories` collection — `firestoreService.ts:35`), which **no in-app code
writes**, so the grid renders `null` in practice. Recorded as a follow-up.
